## Invalid pre-run and metadata correction

The first `MCP_RUN_SINGLE` attempt against server metadata `0.1.0` was not a
retention result. ChatGPT called Create and then Verify in the same assistant
turn and rendered a verification result. The server audit proved both calls.

Classification: `TOOL_SELECTION_DEVIATION`, invalid for Test A.

Only model-facing routing text was then hardened:

- the Create description explicitly forbids automatic Verify for
  `MCP_RUN_SINGLE` and `MCP_RUN_RETAIN`;
- the Verify description contains an exact command whitelist;
- the ordinary Create result no longer says to “use its structured result”;
- the server version was changed to `0.1.1`;
- ChatGPT developer-app metadata was refreshed and all measured runs used fresh
  chats.

Tool count, schemas, tuple fields, `structuredContent`, stateless verification,
and lack of UI/session recovery remained unchanged.

## What the smoke test establishes

For this app version, ChatGPT surface, model setting, and short-dialog setup:

1. ChatGPT read a fresh MCP `structuredContent` result immediately.
2. ChatGPT passed the full result into a second MCP tool in the same assistant
   turn.
3. ChatGPT used previously hidden structured result data in the next user turn
   without making another tool call.
4. ChatGPT passed the complete, unchanged hidden tuple to a stateless verifier
   after one user-turn boundary. The backend proof succeeded.

The fourth observation is the strongest result: it proves transport of all
three original fields across the turn boundary, not merely regeneration of a
plausible token or reuse of a visible value.

Accordingly, the minimal ChatGPT MCP app did **not** reproduce the observed
Custom-GPT-Action failure in this smoke test. A data-only MCP app can therefore
be treated as a viable SkillPilot architecture candidate without requiring an
embedded widget for result retention.

## What the smoke test does not establish

- It is one smoke run per path, not a reliability measurement.
- It covers one immediate user-turn boundary, not a long coaching dialogue.
- It does not cover context compaction, chat resume, browser restart, model
  switching, quota fallback, or a different reasoning setting.
- It does not prove that model-formatted status strings are deterministic. Three
  paths had harmless but real final-format deviations.
- It is an observed product behavior, not a durability guarantee from OpenAI.
- It does not yet establish a safe identity/authentication design for real
  learner data.

## Required follow-up before an architecture decision

1. Repeat B–D at least five times each in fresh chats; ten interleaved runs are
   preferred for an architecture decision.
2. Add realistic multi-turn SkillPilot payload sizes and dialogue length, then
   force or approximate context compaction.
3. Test chat resume and browser/app restart separately from in-chat retention.
4. Test the production-intended model/effort options and record any routing or
   quota fallback.
5. Treat output wording as non-normative. Production workflows should decide
   success from structured tool results and backend state, not exact assistant
   phrases.
6. Design authentication and durable learner-session recovery independently of
   this short-lived model-context result transport.
