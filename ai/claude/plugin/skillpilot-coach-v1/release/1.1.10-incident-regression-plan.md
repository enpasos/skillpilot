# Claude Coach 1.1.10 incident regression plan

Status: **pending**. This plan records a test profile and expected behavior;
it is not acceptance evidence. Test the exact 1.1.10 archive and matching
deployed Claude connector after the candidate digest has been fixed. Do not
reuse results from 1.1.9 or infer installation from OAuth alone.

## Host profile comparison

Test both host profiles on Web and native Android Voice, recording the model,
effort, Thinking setting, browser or app version and installed plugin version
actually displayed by Claude. A SkillPilot plugin cannot select or lock these
settings. Anthropic's [model and effort help](https://support.claude.com/en/articles/8664678-change-the-model-effort-and-thinking-settings)
describes them as host conversation controls and says enabled Thinking can
create an expandable visible summary. Anthropic's [Opus 5.5 announcement](https://www.anthropic.com/claude-opus-5-5)
says that model is unavailable with Thinking switched off.

| Profile | Configuration to verify in Claude | Presentation question |
| --- | --- | --- |
| A: primary regression pair | Claude Opus 5.5, effort **Medium**, Thinking on | Does the coach keep its own reply and spoken output natural while making the correct closure decision? |
| B: comparative fallback | Claude Sonnet 5, effort **High**, Thinking off | Does the same coaching sequence work with this alternative host profile? |

The Product Owner reported profile A for the incident. Profile B is the
comparative fallback; neither profile has passed the 1.1.10 host test. If the requested model, effort or
Thinking option is unavailable on a surface, record that result instead of
silently switching profile. A host-owned Thinking panel cannot be disabled by
the plugin; note its presence separately as diagnostic context. The incident
acceptance criterion concerns the coach's ordinary chat reply and spoken
output, not that separate host panel. Publish Opus 5.5 Medium as a user-facing
recommendation only after the exact candidate passes the complete Web and
Android Voice cases below.

## Sequence checks on Web and Android Voice

Perform each case separately under both profiles on both surfaces. **Ordinary
Web chat messages and Android Voice spoken output are equal acceptance gates.**
Voice reproduces the reported incident; listen to the entire utterance,
including interruptions and the turn after result feedback. Read the complete
ordinary Web chat replies in the same sequence. Capture the learner-visible reply,
spoken output and the order of connector calls without recording
protected values.

1. **Evidence decision and write before result feedback.** Present a task in which the
   learner independently supplies two checks or one genuine multi-step transfer.
   The coach must decide silently from that evidence, call
   `set_skillpilot_mastery` once before result feedback, wait for confirmation,
   then briefly explain what the learner showed and ask about questions or
   continuation. It must not make persistence depend on another learner
   agreement or show a successor before explicit continuation. Also run a
   guided or incomplete variant: the coach must name the missing part and offer
   a targeted check without writing mastery or claiming completion. Reuse the incident's mass-and-scales topic:
   selecting a suitable scale and correcting its nonzero reading, followed by
   mass-versus-volume reasoning. Preserve the fact that the learner mentioned
   steel's much greater density before the coach supplied a density ratio; the
   coach must not later misreport that sequence. If the broader goal still
   needs an actual measurement with a result, unit and suitable precision,
   check that specific gap before claiming goal mastery.
2. **Task-only closure without mastery.** Use a task that is fully solved while
   another aspect of the same goal remains open. The coach must offer to close
   **this task** explicitly without calling the goal complete or writing mastery.
   It may offer practice for the open aspect, but must start that practice only
   after the learner explicitly chooses to continue.
3. **Exam result and learner questions.** Grade a complete exam submission
   against all released criteria. For a pass, verify one immediate
   `set_skillpilot_mastery` call with unchanged evaluation authorization and
   earned points, confirmed before the coach says success was saved. For a
   failure, verify no mastery write or other persisted failure; the coach must
   still give score, concrete feedback, discuss the task, grading and solution, and
   answer questions. The learner may retake the exam any number of times.
   Discussing the solution can make a repeat less informative; record this as
   an unresolved product limitation, not a new retry restriction. In both
   cases, the coach asks whether there are questions or the learner wants to
   continue and waits before new content or a successor image. A plain
   “weiter” cannot regrade the fixed attempt.
4. **No private deliberation in learner presentation.** At startup, during
   teaching, at task feedback and after result feedback, the coach's visible
   answer and spoken audio must contain no internal policy checks, assessment
   weighing, audible self-dialogue, self-instructions, planned tool calls or
   thinking transcript. This applies before and after the closure decision. In
   particular, reproduce the incident pattern where an interruption occurs
   while the learner is still constructing an answer, followed by a request to
   continue. The coach may give a short learning-relevant correction or apology,
   but must not expose its private reasoning. Record the ordinary answer,
   spoken output and host-owned Thinking panel separately. The separate host
   panel is irrelevant to this incident; it fails this check only if the coach
   repeats its contents in the ordinary answer or speaks them aloud.

Passing static instruction checks or MCP contract tests does not pass these
host checks. Leave every 1.1.10 exact-client result `pending` and make no
published user-facing model recommendation until the actual Web and Android Voice runs
are observed and their sanitized evidence is bound to the candidate archive
and revision.
