    ChatGPT App "SkillPilot Coach v1": Deployment and Cutover

    As of: 5 October 2026

    OAuth cutover, 11 September 2026: For the approved new client authentication, follow the profile-specific activation runbook. The target profile uses CIMD with private_key_jwt; existing securely configured Basic connections remain a separate transitional profile. The Basic examples below are not a method fallback for JWT clients. The Claude beta and vendor inquiries do not block this authorization. Implementation alone does not activate a production connection.

    Native desktop integration, 24 September 2026: The uploaded plugin uses the same MCP endpoint and OAuth issuer. An additional chatgpt-native-cimd-public profile supports native CIMD with S256 PKCE; mTLS observe is explicitly authorized for this trial. See configuration and test launch. The enforce acceptance gates below apply to hosted certificate transport.

    Status: Submission 1.0.0 was rejected (REJECTED). The Product Owner has explicitly lifted the ChatGPT development freezes. The current successor 1.1.1 is published via the Git marketplace for the desktop beta; the official OpenAI submission remains DRAFT and the OpenAI directory remains unpublished. Installation and starting a learning session in Windows ChatGPT Desktop have been confirmed by the Product Owner. See unfreeze and review history. The scoped authorizations of 24 September for archive/native CIMD and of 5 October for the existing Git/desktop beta including ordinary GUI launch supplement the original Claude-first sequence. The Product Owner performs the GUI/server rollout; local changes do not constitute a resubmission. The V1 contract continues to use the dedicated mcp-coach-v1.skillpilot.com origin with server-authenticated HTTPS, OpenAI connector mTLS, and OAuth/PKCE. Actual production state and the required enforce mode for hosted certificate transport must be re-verified before any submission. The separately authorized native desktop beta using observe remains distinct from that path. Permanent ID, provider notice, and Level 2 configuration remain exclusively inside the first-party WebGUI.

    This runbook activates the multilingual, chat-first MCP learning coach with two separately bound MCP Apps UIs: the read-only learning-goal image viewer and interactive flashcard practice. The MCP server, OAuth authorization server, UI resource delivery, and SkillPilot domain logic run inside the existing Spring Boot process. The Node MCP server under ai/openai app/ remains a local regression testbed; it also hosts the verified source implementation of the UI components whose self-contained build artifacts are copied into Spring Boot resources.

    The canonical responsibility boundary between chat client and backend is defined in the communication contract. Product and provider architecture are documented in the SkillPilot-owned coach architecture. The binding identity and session flow is documented separately in openai-mcp-oauth-learner-session-architecture.md. Package, contract, and lifecycle versions follow the versioning and lifecycle plan; release, rollback, and retirement follow the V1 release runbook. In particular, ChatGPT manages OAuth access and refresh tokens automatically; users never enter OAuth tokens, an OAuth client secret, or a permanent SkillPilot ID in chat. However, every explicit authorized launch via the first-party web interface creates an independent learningSessionId with an absolute 24-hour lifetime. During an ordinary desktop beta launch, the prepared message is copied into a fresh chat with the plugin selected. Dedicated Recall/exam launches retain their browser-launch contracts. SkillPilot inserts this reference automatically into the short start message; ChatGPT passes it unchanged to every domain MCP tool.

    2. Discovery Bootstrap and OAuth Values of the Legacy Compatibility Profile

    The production contract uses Authorization Code with PKCE S256 and exactly one pre-registered confidential OAuth client for the SkillPilot Coach v1 line. Its fixed client ID, long random client secret, exact callback allowlist, fixed MCP resource, and fixed scopes are configured on both sides by the app author. ChatGPT authenticates at the token endpoint using client_secret_basic; SkillPilot accepts neither none nor open Dynamic Client Registration, CIMD, or private_key_jwt in this active legacy production profile.

    The secret is protected configuration exclusively in ChatGPT and SkillPilot. It must never appear in the repository, browser, start message, tool arguments, or logs. PKCE additionally binds the authorization code to the verifier generated by ChatGPT. Standard server-authenticated HTTPS remains mandatory. At the dedicated MCP edge, ChatGPT additionally presents an OpenAI-managed client certificate; SkillPilot does not need to request its own certificate for this.

    ChatGPT administration probes the MCP URL before revealing its advanced OAuth settings. At the same time, the full SkillPilot authorization server requires the app-specific callback URL. An explicit, stateless bootstrap mode exists for this purpose:

    1. Leave full operation disabled and set exclusively SKILLPILOT_OPENAI_COACH_V1_BOOTSTRAP_ENABLED=true.
    2. After restart, verify the four discovery URLs and the constant MCP 401. Bootstrap registers neither tools nor OAuth client, token endpoints, learner services, or a coach health contributor.
    3. In ChatGPT app administration, select Server URL, the production MCP URL, and OAuth.
    4. Generate a fixed client ID dedicated solely to this app and a long random client secret. Configure the exact same values in ChatGPT and SkillPilot; never copy the secret into documentation or tickets.
    5. Copy the app-specific production callback URL shown there, formatted as https://chatgpt.com/connector/oauth/{callback_id}, unchanged.
    6. Configure multiple real callback URLs as a comma-separated list. Do not add any example or legacy URL that does not appear in app administration.
    7. Select client_secret_basic as token-endpoint authentication in ChatGPT. Disable bootstrap and atomically enable full operation with client ID, secret, callback, OAuth, MCP, and write operations enabled. A read-only canary is an intentionally non-production diagnostic state.

    The bootstrap MCP endpoint rejects every method and any arbitrary Bearer values with 401 plus WWW-Authenticate. Authorization, token, revocation, and introspection endpoints remain 404 during bootstrap. OpenAI documentation defines this challenge/metadata contract as the discovery mechanism; whether a specific ChatGPT UI build unlocks its advanced settings with it is still verified in practice. If a UI issue occurs, the security contract is not relaxed. Local rate limiting and data-minimized status telemetry already protect this public bootstrap edge; across multiple instances, a shared gateway rate limit remains required in addition.

    Without a client ID or callback list, Spring startup intentionally aborts when OpenAI V1 OAuth is enabled. Bootstrap and full operation must also never be enabled simultaneously; that misconfiguration aborts startup.

    3. Runtime Configuration

    For a safe cutover, code and additive Liquibase migrations can first be verified in a separate read-only canary. Full production operation, by contrast, requires write operations to be enabled and uses server-authenticated HTTPS on the dedicated V1 vHost, OpenAI connector mTLS, and mandatory OAuth/PKCE with exact resource/audience and scope checks. The separate host isolates domain verification, plugin lifecycle, and client-certificate verification. The existing skillpilot.com vHost is not fundamentally restructured; it only receives the narrow 404 block against MCP/internal path aliases described below.

Including it at the global top level outside http {} triggers server directive is not allowed here and is invalid.     The local rate limiter separates MCP, OAuth, Cockpit launch, and metadata traffic. The first-party launch route and the MCP path enforce independent budgets.

    Network-scoped budgets use solely the remote address normalized by the servlet container; the limiter parses no forwarding headers. Consequently, the production reverse proxy must strip or overwrite incoming Forwarded/X-Forwarded-* headers, and the backend port must not be directly reachable from the public internet. Across multiple backend instances, a shared gateway rate limit is mandatory in addition; the in-process limiter is intentionally only a last local line of defense. Throttled requests return 429 with Retry-After and no-store.

    The general request-body logger skips MCP, provider OAuth, and OpenAI Cockpit launch paths completely. In particular, authorization codes, PKCE verifiers, access/refresh tokens, and typed learning-goal start intents must never appear as request bodies in application logs, even with debug logging enabled.

    7. Cockpit Canary and Cutover

    The variant is an explicit per-frontend-artifact decision. The stable production entry point at the repository root sets the current product choice openai-mcp, while the generic deployment engine still accepts no implicit default. Every engine invocation must specify exactly one of visible-session, openai-mcp, or legacy.

    For the multilingual MCP canary or cutover, the stable production command is:

    ./deploy_skillpilot.sh

    The repository-root entry point deliberately sets the production variant to openai-mcp and delegates to scripts/deploy.sh. The engine still rejects any missing or invalid variant value, aborting before Git update, build, and service restart. Artifact verification thus stays enforced without requiring a build variable to be typed manually on every routine deployment. A rollback explicitly overrides the variant via --coach-variant visible-session on that same entry point. Any VITE_SKILLPILOT_COACH_VARIANT still lingering in the shell environment is deliberately ignored by the production entry point.

    The build records the resolved variant inside backend/src/main/resources/static/version.json under coachVariant and inside backend/src/main/resources/static/index.html as <meta name="skillpilot-coach-variant" ...>. Immediately after the frontend build, scripts/deploy.sh checks both values with scripts/verify_frontend_coach_variant.mjs, stopping before backend build and restart on any mismatch. After restart, that same verification script fetches version.json and index.html again cache-free from SKILLPILOT_BASE_URL (default: https://skillpilot.com), causing a stale visible-session build behind a proxy or cache to fail the deployment as well.

    The OpenAI MCP variant uses the single V1 app across all approved languages. The server-created learning session fixes its communicationLocale at launch, while plugin control plane and tool contract stay neutral English. Adding a language creates neither another host nor another app.

    The ordinary GUI entry Start learning (Lernen starten) offers Claude and ChatGPT Desktop (Beta), and the Cockpit entry returns to this provider choice. Selecting ChatGPT calls POST /api/ui/learners/{skillpilotId}/openai/v1/launch and presents the prepared start message for copying into a fresh desktop chat via the button Prepare learning with ChatGPT (Lernen mit ChatGPT vorbereiten). ?coach=chatgpt-desktop serves as an optional preselection; ?chatgptTest=1 remains a compatible preselection without a separate launch card. The confirmed Git/desktop beta route uses no automatic browser launch. Dedicated Recall and exam launches keep their own intent and browser-launch contracts and do not constitute desktop acceptance of this ordinary launch. Special launches are prepared server-side as a narrow, auditable intent schema; free-form instruction text from the browser is never accepted. Every ordinary successful call creates a fresh learningSessionId with an exact 24-hour absolute lifetime regardless of app authorization status and embeds it in that same prompt. The permanent SkillPilot ID stays outside the OAuth principal, chat, URL prompt, and tool contract. ChatGPT must pass the session ID from the prompt unchanged on every domain MCP call. Because the session ID is not bound to a single chat conversation, it can be reused in a fresh chat within its lifetime, though neither usage nor OAuth refresh extends it. Exclusively the explicitly enabled, request-local first-party diagnostic field described above may shorten an individual test session without altering this default.
