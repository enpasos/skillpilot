    The initial code legend listed 8 GVR and 18 CQR codes. At that baseline, 5 GVR codes were HARD; GVR-006, GVR-012, GVR-013 and all 18 CQR codes were PARTIAL.

    The bounded implementation is complete: the executable portions of the work packages were delivered in a PR with terminal green remote CI and integrated into main, with subsequent green integration CI. Unfulfilled target items remain explicit, and the register states exactly which domain each gate covers. The full HARD target still requires genuine endpoint visibility evidence for the four remaining scopes in WP5, and independently evidenced semantic route coverage as described in WP6.     3. What HARD means in this plan

    A legend row may be graded HARD when all four hold:

    • H1 – Derived or pinned domain. The set of landscapes or scopes the gate covers is computed from the complete catalog or pinned in a committed register whose coverage is itself checked. It cannot shrink silently.
    • H2 – Direct failure. CI fails on any violation inside that domain. It does not depend on a floor happening to cover the affected subject.
    • H3 – No bypass. No environment switch, not_configured result or optionally attached rule lets a violation through.
    • H4 – Main acceptance. The claim is true for the whole domain on main, with terminal green CI for the merged head. Before merge, a candidate may document H1–H3 enforcement and passing candidate evidence, but must not claim H4 or main acceptance. Candidate HARD legend entries describe the code under review, not an authorized merge or an accepted-main result.

    Two classes of rule follow from this:

    • Class I – catalog invariants. Must be pass for all 21 catalog curricula at all times: CQR-001, CQR-002, CQR-501.
    • Class II – milestone and scope obligations. Bind a curriculum or QA scope from the milestone at which it is pinned: CQR-000, 003, 004, 005, 101–104, 201–203, 301–303, 401. The CQR-104 obligation applies only to its eight explicitly pinned visibility scopes; the four remaining route profiles carry documented unmet visibility obligations, not silently skipped required results.

    • Never lower or remove a floor, add a floor exception, bulk-decide a review queue or hand-edit a generated file to make a check pass.

    • After any curriculum or generator change run npm --prefix app run quality:curriculum-status and confirm that no protected maturity dropped.
    • Scope every search to a concrete directory. Never search from the repository root; tmp/ and site/ are large.
    • Resolve routine implementation findings and record deviations in section 9. Continue independent work when a package hits a genuine evidence gap. Do not fabricate missing reviews, source evidence or semantic classifications.
