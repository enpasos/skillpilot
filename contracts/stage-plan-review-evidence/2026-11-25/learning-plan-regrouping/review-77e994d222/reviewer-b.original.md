**Decision: request changes.** A learner can have outstanding scheduled work in a plan marked current and be offered work from outside that plan. An edit can also create an unrelated section/goal combination that did not exist before. Both affect the meaning of “as long as it still works.”

### 1. Which paths apply the decision?

**Partial.** Keeping an originally captured goal after its section changes is appropriate if the goal is still in the personal subject scope and can be worked through. Stored plan reads check current subject selection, scope, graph and ordering in `LearnerService.java:4583–4604`. Plan details and the precondition for continuation use that check in `LearnerLearningPlanService.java:1532–1541,1742–1763`. The signed import applies retirement filtering, normalization and the revised focus check in `LearnerService.java:14888–14910`. The edit, preview and activation entry points all use the same preparation in `LearnerLearningPlanService.java:923–932,967–974,1022–1036,1440–1485`. I found no overlooked strict fingerprint call in those paths.

A genuinely new plan has an empty retention set. A newly introduced out-of-section atom is rejected. Each supplied focus must still resolve to counted targets of this subject. Milestone lists still validate each root, while the historical descriptive single milestone field retains its existing semantics. Unit assignments are excluded by `LearnerLearningPlanApi.java:84–89`, new or edited assignments require the matching edition and ordered parts, and resuming a paused assignment checks the current offer (`LearnerService.java:5078–5097,5241–5258`, `LearnerLearningPlanService.java:1454–1465,852–855`, `LearningPlanScopeResolver.java:80–88`). The edit exception is nevertheless too broad for replacements, including through preview and activation (answer 2). The runtime still consults the old focus for scheduled work (answer 5).

The teacher frontend has two distinct user-visible routes. A server-only copy reuses the stored atom IDs. A local template materializes today's projection and flags a projection-only difference for review. Confirmed activation sends the chosen copy, so confirming the newly projected template can replace the old workload. ### 2. Where does retention come from?

**The scope boundary holds for ordinary plan atoms. The block boundary does not.** On edit, the server loads one learner/landscape row and checks its revision. It then pools all ordinary block atoms, including inactive blocks, and never compares the old block ID or old focus to the submitted block (`LearnerLearningPlanService.java:1440–1453,1472–1477,2702–2707`). An edit that replaces a block, changes its focus, or moves a previously captured atom to another block passes the new focus check if the new root resolves and the atom is in scope. Such an association can be authored today with no regrouping. Valid new goals added on one save also enter the pool on later saves. The problem is the loss of the historical association, even when the submitted plan contains exactly the same atoms. Preserve the old block and focus association for edit-time exceptions, while still allowing ordinary title/date edits and newly valid selections.

Cross-subject and out-of-scope ordinary atoms still fail. Planning scope starts from `projection.targetGoalIds()`, filters to subject and counted nodes, and normalization checks that set before considering previous capture (`LearnerService.java:4436–4445`, `LearnerLearningPlanService.java:2169–2171,2216–2225,2287–2289`). The new focus overload's structural-node check alone would not prove Level-2 membership, but these production callers first normalize. The import takes retention from the signed archive's ordinary blocks after retirement filtering. It verifies the archive and applies its selected and Personal Curriculum before validating its plans (`LearnerService.java:14771–14793,14822–14837,14861–14862,14894–14907`). Thus a recipient's *previous* personal selection is not the restored selection. The full archive is signed, but a signature on a stored association alone does not prove its original focus was appropriate.

### 3. Can the reversed test hide damage?

**Yes. The test itself contains a concrete counterexample.** Its original block schedules both choosing and creating a representation under the representation cluster (`LearnerServiceTest.java:5256–5266`). The altered block changes its focus to *choosing a representation*, while retaining both atoms, and the new assertion accepts it (`LearnerServiceTest.java:1851–1862`). That focus is a specific assessment-sized goal with no children (`curricula/DE/Gymnasium/canonical/DE_DEU_S_GYM_CANONICAL_MATHEMATIK.de.json:33326–33339`). Moving goals between curriculum sections cannot make one unchanged leaf the former section of a different leaf. Once choosing is mastered, creating remains scheduled outside that focus. Keep a separate negative test for this shape and a positive one for an actual section with moved children. A historically wrong but still resolving *section* can be indistinguishable from a real regrouping in legacy data. That residual ambiguity makes an executable fallback for legitimate captures especially important.

### 4. Is import equivalent to reading the stored plan?

**Equivalent effective work in the supplied already ordered examples, different capture identity and a real boundary on equivalence.** Reading filters retired goals for evaluation while raw export retains stored blocks (`LearnerService.java:4583–4604,14741–14765`, `LearnerLearningPlanService.java:2750–2764,2775–2790`). Import writes the filtered, normalized and prerequisite-ordered blocks into a new plan, calculates a fingerprint against today's graph and focuses, sets revision 1 and a new capture time, and replaces the prior rows after preparing the whole list (`LearnerService.java:4755–4768,4790–4805,14908–14938`). The portable schema carries only landscape, label and blocks (`LearnerLearningPlanApi.java:262–264`). An unchanged read preserves the old fingerprint, revision and time. A fresh fingerprint may coincide if all its inputs match. The GK/LK tests assert block equality on restore, not equality of historical fingerprints or revisions (`ClaudeV1CompletionRouteIntegrationTest.java:1743–1751,1798–1809`).

“Every plan that is stale on read aborts import” is too broad. The read requires exact equality to normalized blocks and to current prerequisite order and checks the current graph. Import normalizes and can repair order. For an order that changed but is repairable inside one block, reading leaves the old schedule stale, whereas import can store a current schedule with a different order. The captured curriculum ID is also absent from the portable format. These are existing distinctions, not newly preserved history (`LearnerService.java:4587–4605,5323–5336,5368–5393,14898–14920`). A missing section, unknown current atom or retired-only active plan still prevents a normal restore. Block validation and fingerprinting both use the relaxed call on this path. Signature, receipt/restorable-card validation and imported navigation revalidation operate separately (`LearnerService.java:14777–14793,14856–14862,14980–15016`).

### 5. What can the learner actually do?

**Blocking navigation finding.** Cockpit and coach calculate today's status from the same evaluator (`LearnerLearningPlanService.java:338–361`). Ordinary plan progress and quotas include the captured active atoms, including moved atoms (`LearningPlanScopeResolver.java:59–63`, `LearnerLearningPlanService.java:688–704`). A scheduled candidate, however, must appear on the frontier for the **old block roots**, or have an opening on that frontier (`LearnerLearningPlanService.java:1819–1839,2093–2115,2140–2147`). Section focus expands to its current targets/descendants (`LearnerService.java:4118–4124,8148–8164,15047–15066`). With its prerequisites and openings satisfied, an eligible moved atom outside that frontier is skipped as scheduled work. If no scheduled candidate remains, ordinary explicit continuation can pick the first eligible subject goal, including unrelated work. An active versioned assignment suppresses that subject fallback. Plan detail can instead advertise an available assessment part, or no candidate, while a moved ordinary goal remains due (`LearnerLearningPlanService.java:1761–1789,1987–2010`). Automatic resume consults the due-only path (`LearnerLearningPlanService.java:532–535,1645–1663`). The GK/LK regression's non-null next goal while the entire current E.1 is also open does not demonstrate reaching either moved goal (`ClaudeV1CompletionRouteIntegrationTest.java:1779–1803`).

Post-mastery automatic handoff is a separate implementation: it computes the frontier over the selected learning scope and may add the selected external atom to the persisted section focus (`LearnerService.java:10475–10512,10564–10585`). One successful handoff therefore would not establish ordinary resume or explicit continuation. A fix should use the retained goal's current atom focus, or its required opening, consistently for candidate selection and transition while preserving the original schedule and display label. Verify the *specific* scheduled atom/required opening after all original-section work is completed, including with an active assignment.

The pilot's section policy still evaluates optional assessments from the selected roots' **current** targets, validates the contract and removes matching optional IDs on effective read. It does not relocate ordinary moved goals or make them reachable (`LearnerService.java:491–510,519–534`, `LearnerLearningPlanService.java:2793–2815`). The versioned assignment itself still matches its exact offer/parts and shows unavailable otherwise (`LearnerLearningPlanService.java:3272–3293`). No extra unit-assignment credit follows from being retained.

### 6. Can results survive a genuinely incompatible plan?

**Yes, as separately identified historical data; this needs a deliberate product change.** Today the public restore is transactional. A plan-validation exception at the end rolls back the earlier writes to results and learner state (`LearnerService.java:14771–14793,14840–14862,14903–14910`). For a well-formed signed archive with a plan made incompatible by curriculum evolution, preserve that raw capture and an explicit outdated reason in history while committing valid results and independently valid plans atomically. Report which plan needs repair. Keep signature, shape/size, receipt and card validation and infrastructure errors distinct from a known curriculum mismatch. Keep the capture out of scheduling, waivers, exam focus and coach continuation until explicit repair. Merely suppressing the exception and placing the raw row among executable plans would be insufficient: followed-scope/exam discovery reads those rows and checks shape/curriculum along paths that do not run full plan compatibility (`LearnerService.java:5194–5213,5227–5237,10358–10365`, `LearnerLearningPlanService.java:1908–1923`). A separate historical store or an explicit state observed by every such reader could provide this boundary without ascribing a new current fingerprint to old data.
